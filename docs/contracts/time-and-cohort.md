# 時間與 cohort 語意契約

- 狀態：step-1 定稿；之後的變更必須在同一個 PR 更新本文件與對應測試
- 適用範圍：所有抓資料、建特徵、算標籤、訓練、排名與回測的程式碼
- 資料來源：文中所有時間戳都是 2026-09-26 從 Data Center 實際查到的值（見 §10）

本文件回答三個問題：一個 cohort 是什麼、它在哪個時點能看到哪些資料、它的標籤何時才能拿來訓練。

---

## 1. 名詞

| 名詞 | 意義 |
|---|---|
| cohort | 一次選股決策。v1 每月一個 |
| playbook date | 做出這次決策的交易日 |
| 資訊截止點（information cutoff） | 資料必須在此時點前**已公開**才能使用 |
| 知識截止點（knowledge cutoff） | 資料必須在此時點前**已被 Data Center 記錄**才能使用 |
| 系統截止點（system cutoff） | Data Center 在此時點前已記錄的一切資料，不論是否已公開；只用於稽核 |
| 進場日 / 出場日 | 標籤報酬的起點與終點交易日 |
| `label_available_at` | 標籤的所有輸入都已公開的時點 |
| 營收截止日 | 上市櫃公司公布上月營收的期限，定義見 §3 |

---

## 2. 時間的表示方式

- 截止點一律是**帶時區位移的時間戳**，例如 `2024-07-11T04:00:00+08:00`，絕不是單純日期。
  Data Center 的可用時點精確到日內：D 日的日價格在 D+1 03:00 台北時間才可用。只寫「2024-07-11」無法分辨當天 03:00 公布的資料算不算。
- 日曆日期（交易日、營收月份、除權息日）一律以 `Asia/Taipei` 解讀。
- 時間的比較一律用絕對時間，不比較字串，也不比較本地時間。
- 交易日一律以 `/v1/trading-days` 為準。它包含颱風停市等臨時休市，例如 2024-07-24、07-25 不是交易日。
- 程式碼傳給 Data Center 的 `information_as_of` 一律是明確的時間戳，不傳 `latest` / `now`。
  `knowledge_as_of` 的規則見 §5。

---

## 3. Cohort 識別與 playbook date

v1 每個月一個 cohort。

```text
cohort_id          "YYYY-MM"，即 playbook date 所在的月份 M
營收截止日 D_M      M 月 10 日；若不是交易日，順延到下一個交易日
playbook date P_M  D_M 之後的第一個交易日（嚴格晚於 D_M）
```

- P_M 一定落在 M 月內，所以 `cohort_id` 與 playbook date 一對一。
- 規則只用交易日曆，不用任何「當年主管機關是否延長期限」的資訊。主管機關延長期限的月份，按規則處理：當時還沒公布營收的股票，該月不列入股票池（見 §8）。
- 決策使用的是 M-1 月的營收。

例：

| cohort | 10 日 | 營收截止日 D_M | playbook date P_M |
|---|---|---|---|
| 2024-06 | 週一，端午節休市 | 2024-06-11 | 2024-06-12 |
| 2024-07 | 週三 | 2024-07-10 | 2024-07-11 |
| 2024-08 | 週六 | 2024-08-12 | 2024-08-13 |
| 2024-09 | 週二 | 2024-09-10 | 2024-09-11 |

## 4. 三個截止點與 Data Center 參數的對應

| 截止點 | 定義 | Data Center 參數 | 過濾欄位 |
|---|---|---|---|
| 資訊截止點 T_C | P_C 當天 04:00 `Asia/Taipei` | `information_as_of` | `available_at` |
| 知識截止點 K_C | 依執行模式而定（§5） | `knowledge_as_of` | `recorded_at` |
| 系統截止點 | 僅供稽核（下述） | `system_as_of` | `recorded_at`，不看是否已公開 |

**為什麼資訊截止點是 04:00：**

- 前一個交易日的日頻資料在 03:00 可用，04:00 已包含，並留一小時餘裕。
- 04:00 早於 09:00 開盤，所以不論 step-2 選擇開盤價或收盤價進場，進場交易都晚於截止點；開盤前有五小時可以跑完 production。
- 本文件的數字以 04:00 與 08:00 兩個截止點各量一次，結果完全相同：實測 03:00 到 08:00 之間沒有任何資料公布。
- 月營收與財報的 `available_at` 是公布日的 23:59:59。playbook date 當天才公布的營收，在截止點時看不到。

**系統截止點：**

- `system_as_of` 不能與 `information_as_of` / `knowledge_as_of` 並用。
- v1 只用它做稽核與除錯，例如查 Data Center 在某時點到底記錄了什麼。
- 抓特徵、算標籤、訓練、排名與回測都**不得**使用系統截止點。
- 帶系統截止點的 `PitContext` 自成一種模式，特徵 API 與標籤 API 必須拒絕它。

**進場日不是截止點：**

- 任何抓特徵資料的 API 都只接受 `PitContext`，不接受日期。
- 不存在任何從進場日推導截止點的函式。
- T_C 早於進場交易，但兩者是分開定義的兩個量，不能互相換算。

## 5. 兩種執行模式

| 模式 | `information_as_of` | `knowledge_as_of` | 意義 |
|---|---|---|---|
| production（正式） | T_C | 執行時點 t_run，且 T_C ≤ t_run < 進場交易 | 真正的 PIT：當時公開、當時已記錄 |
| reconstruction（重建） | T_C | 重建時點 t_recon，明確時間戳，記錄在 artifact 中 | 當時已公開的資料，以 t_recon 的紀錄為準 |

- 兩種模式的 `information_as_of` 相同，差別只在 `knowledge_as_of`。
- 排名 artifact 的種類（`production` / `reconstruction`，step-19）與這兩種模式一一對應。
- **重建模式的已知限制：**
  - 它看得到 T_C 之後才記錄的更正。
  - Data Center 的歷史資料是 2026 年回補的。例如 2330 在 2024-07 的日價格，`recorded_at` 是 2026-09-16，所以 `knowledge_as_of=2026-09-01` 時查不到任何列。
  - 因此 2026 年以前的 cohort 只能以重建模式執行，無法得到真正的 PIT。
- **已儲存的衍生資料集只接受 `knowledge_as_of=latest`：**
  - 例如 `valuation-metrics`、`technical-indicators`。傳入明確時間戳會回 400，即使那個時間戳就是一分鐘前。
  - 使用這類資料集時，兩種模式都傳 `latest`。
  - 同時在 provenance 記錄回應中的 `pit` 區塊與每列的 `computed_at`，並把回傳列納入資料集雜湊。
  - 這類資料集重跑時不保證得到相同數值，這是已知限制。
- observed 資料集與即時計算的 `*-pit` 資料集接受明確的 `knowledge_as_of`。在重建模式下，同一個 t_recon 可以重現相同結果，前提是 Data Center 不刪除紀錄。

**財報公布時間在歷史與近期不一致（重建模式必須知道）：**

| 財報季度 | `available_at` |
|---|---|
| 2025 Q3（含）以前 | 每季所有股票共用同一個日期（法定期限當天或之後第一個工作日的 23:59:59，例如 2025 Q3 是 2025-11-17 週一），例如 2023 Q4 全部是 2024-04-01、2024 Q1 全部是 2024-05-15 |
| 2025 Q4 起 | 每檔股票各自的實際公布時間，例如 2330 的 2025 Q4 是 2026-03-04 01:02 |

歷史 cohort 看到財報的時點，比實際公布晚。這不會造成資料洩漏，但特徵會比 production 更舊。所以 2026 年以前的回測與 production 在財報時效上有系統性差異，比較兩者時必須說明。

## 6. PIT 層級

| 層級 | 意義 |
|---|---|
| 列層級 PIT | 某列在截止點是否可見，依 `available_at`（及 `recorded_at`）判斷 |
| 值層級 PIT | 某個數值是由截止點時已知的輸入版本算出來的 |

各類 Data Center 資料能達到的層級：

| 資料類型 | production | reconstruction |
|---|---|---|
| observed | 值層級 | 列層級；值是 t_recon 時的最新版本 |
| 已儲存的衍生資料集（`inputs = "latest"`） | 列層級 | 列層級 |
| 即時計算的 `*-pit`（`technical-indicators-pit`、`adjusted-prices-pit`） | 值層級 | 值層級，以 t_recon 為準 |

各資料集必須達到哪個層級，於 step-2 的 `docs/contracts/data-dependencies.md` 逐一決定。

## 7. 進場、出場、標籤期間與 `label_available_at`

```text
進場日 E_C             = P_C
出場日 X_C             = P_{C+1} 的前一個交易日
標籤期間                = [E_C, X_C]，長度隨月份不同，約 19–23 個交易日
label_available_at(C)  = 出場日日價格列的 available_at
                         規則為 exchange_daily_settled@1：X_C 的下一個日曆日 03:00 Asia/Taipei
```

- 用開盤價還是收盤價、還原還是原始價格，於 step-2 決定。上面的日期與價格慣例無關，因為同一天的開盤價與收盤價在同一列、同時可用。
- `label_available_at` 以實際查到的 `available_at` 為準。資料尚未存在時，以上述規則推算的值作為下限，實際值只會更晚。
- 標籤期間內的除權息事件，其可見時點是除權息日 00:00，早於出場日，所以在 `label_available_at` 時都已可見。
- **性質**：X_C 的下一個日曆日不晚於 P_{C+1}，所以 `label_available_at(C)` 不晚於 P_{C+1} 03:00，早於 T_{C+1}（P_{C+1} 04:00）。也就是說，cohort C 的標籤在下一個 cohort 的截止點時已完整。
  - 例：2024-07 cohort 出場日 2024-08-12（週一），`label_available_at` = 2024-08-13 03:00，T_{2024-08} = 2024-08-13 04:00。
  - 例：出場日在週五時，`label_available_at` 是週六 03:00。實測 2330 在 2024-07-26（週五）的日價格，`available_at` 為 2024-07-27 03:00。

## 8. 股票池語意（資格規則）

cohort C 的股票池，是同時滿足以下條件的股票。資料來源與實作於 step-7。

1. 在 `/v1/stocks` 的涵蓋範圍內：上市櫃普通股，不含 ETF、特別股、TDR、權證、創新板。
2. 有一段掛牌期間涵蓋 P_C，即 `listed_on ≤ P_C < delisted_on`。
3. **M-1 月營收在 T_C 可見**：該股票 M-1 月的 `monthly-revenues` 列在 `information_as_of = T_C` 下查得到。查不到就不列入 cohort C。
4. P_C 的前一個交易日有成交（成交量 > 0），且該列在 T_C 可見。停牌中的股票無法在進場日交易。
5. 不是金融保險業：`/v1/stocks` 的 `industry` 為「金融保險業」者一律排除（2026-09-26 決議）。部分下市金融股的 `industry` 為 null（2867、2888），處理方式見 ROADMAP Phase 0。

規則 3 的實際影響（2020-02 到 2026-08，共 79 個 cohort）：

- 每月被排除的股票中位數為 6 檔。
- 排除超過 1% 的 cohort：

| cohort | P_C | 被排除 / 當月最終公布營收的股票數 |
|---|---|---|
| 2020-02 | 2020-02-11 | 433 / 1648（26.3%） |
| 2022-02 | 2022-02-11 | 596 / 1709（34.9%） |
| 2023-04 | 2023-04-11 | 547 / 1746（31.3%） |
| 2026-06 | 2026-06-11 | 310 / 1818（17.1%） |
| 2020-09、2024-11、2024-12、2025-02、2025-03、2025-04 | — | 各 1.0%–1.6% |

2020-02、2022-02、2023-04 看起來是主管機關延長了期限：大量營收在 10 日之後的一兩個交易日才公布。v1 接受這幾個月股票池變小，不維護期限例外表。回測報告必須列出每個 cohort 的股票池大小，讓這些月份看得出來。

## 9. 目標 cohort 的排除規則

訓練目標 cohort C 的模型時，cohort K 的標籤可用於訓練，若且唯若：

```text
K 早於 C
且 label_available_at(K) ≤ T_C
且 K 的標籤所需的價格資料，在 C 的 PIT 情境下確實查得到
```

因此以下一律排除：

- C 本身：它的標籤在 T_C 時根本還沒發生。
- 所有晚於 C 的 cohort。
- `label_available_at` 晚於 T_C 的較早 cohort。

依 §7 的性質，在 v1 日曆下最近可訓練的是 C-1。第三個條件處理 production 模式下 Data Center 資料擷取落後的情況：即使規則上已可用，資料還沒進來就不能用。

## 12. 交給 step-4 的不變條件（會先寫成失敗的測試）

1. 從單純日期或 `entry_date` 建立 `PitContext` 會失敗。
2. 沒有時區的截止點會失敗。
3. 帶系統截止點的 `PitContext` 不能用於特徵或標籤。
4. production 模式下 `knowledge_as_of` 早於 `information_as_of` 會失敗。
5. 給定交易日曆，`P_M`、`D_M`、`X_C`、`label_available_at` 與 §3、§7 的例子一致（2024-06、2024-07、2024-08）。
6. 對每個 cohort C，`label_available_at(C) < T_{C+1}`。
7. 目標 cohort C 的訓練集不含 C 本身與之後的 cohort，也不含 `label_available_at > T_C` 的 cohort。
8. M-1 月營收在 T_C 不可見的股票不在 cohort C 的股票池中。
